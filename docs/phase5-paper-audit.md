# Phase 5 durable paper execution audit

This audit maps the Phase 5 implementation and exit criteria in [the Go runtime plan, §12](go-runtime-plan.md#12-migration-phases-and-gates) to the PostgreSQL paper runtime, tests and retained process evidence. The literal **local durable-paper gate is complete** through clean source `883704c`, with the evidence retained in `bdd762b`. The full plan remains open: a PostgreSQL fence for simulated paper effects does not isolate a private exchange sender, and process recovery is not a database backup/restore drill.

## Recovery evidence boundaries

The local proofs have distinct scopes. Three repeated ordinary-process recovery trials killed and resumed one synthetic paper account while a bystander remained active and HTTP reads continued; each trial completed the financial and process audits, but each had zero observed-minus-processed source debt at the crash boundary. As documented in [`benchmarks/results/paper-recovery-load-20261029/README.md`](../benchmarks/results/paper-recovery-load-20261029/README.md), this is recovery under modest read demand, not a backlog-drain or headroom measurement.

Separately, [`TestFactQuantumBoundsCountAndElapsedInsideTransport`](../internal/runtime/fact_quantum_test.go) stores 512 distinct partial fills as one accepted paper outcome and reconstructs them under a fresh owner. It checks all 512 fills, exact final balances (1.0256 BTC and 997.4630656 USD), cleared reservations, a paused parent, readiness, and matching observed/processed cursors. [`TestFactQuantumControlAckPrecedesPrefixCompletionAndMarketsStayOrdered`](../internal/runtime/fact_quantum_test.go) also checks controls and reads during a bounded reduction prefix. These are real PostgreSQL-backed fresh-owner tests, but they are not an ordinary daemon SIGKILL trial with accepted backlog.

[`TestPaperProcessAcceptedBacklogRecoveryWithBystanderDemand`](../cmd/liquiditylabd/paper_load_recovery_backlog_test.go) adds an ordinary-daemon SIGKILL/reap/resume trial with an explicit accepted partial batch. Before the read schedule, it confirms a Linux SIGSTOP, no open victim database transaction, an ownership lease with more than ten seconds remaining, and a caught-up open passive child, then records 128 harness-authored partial fills through the owned transport-observation path. The read schedules start immediately before SIGCONT, which releases the victim into the measured schedule. A pass requires a strict nonempty, not-fully-applied batch prefix after reap, with accepted debt and the child reservation retained, followed by complete recovery and financial audit. The post-reap prefix may be longer than the first prefix observed before SIGKILL; it must still remain a strict prefix. This fixture is not emitted by the ordinary 2 Hz source and does not measure natural feed backlog or capacity. The [retained clean cohort](../benchmarks/results/paper-accepted-backlog-20261029/README.md) passes three repeats from `883704c`: post-reap snapshot/execution prefixes are exactly 2, 1 and 2 of 128, each with debt 6−5=1 and a positive hold. All 128 fills recover under the next epoch, paused, with exact BTC 0.003 / USD 19.69973003 balances and 0.00029997 USD fees. Independent rational arithmetic and read-only retained-database inspection verify the final accepted observations, payload hash, executions, snapshots, cashflows, pins and drained obligations. The full uncached Go race run passes with real development PostgreSQL and actual Python/replay paths: 1,078 test/subtest pass events, zero skipped test cases, daemon 66.036 s and runtime 82.910 s. Every named Go regression in this audit appears among those pass events. The 512-fill fresh-owner test remains separate evidence.

## Local sign-off and separate release gates

- **Natural feed backlog and headroom:** the clean 128-fill process fixture proves one accepted-backlog crash boundary. It does not prove recovery of naturally accumulated source backlog, supported source rate or admission headroom. Those operational measurements remain open.
- **Post-reap audit correctness:** `87a0ca3` adds an account-row-lock barrier before collecting the crash snapshot and execution rows. Its deterministic writer/observer regression proves the audit waits for an already received database commit after client reap. The failed earlier full-suite attempt and this correction remain recorded in the verification history; no financial or strict-prefix assertion was relaxed.
- **Private exchange sender isolation and failover:** not supplied by `postgres-paper-v1`. A database epoch can reject stale PostgreSQL writes, but cannot fence a live remote connection. The plan's reconciliation, exchange-confirmed fill/cancel, and private snapshot/stream handoff remain separate implementation and pilot gates.
- **Backup/restore:** no backup/WAL restore drill into an isolated paused deployment is evidenced here. Process restart against the same live database is not a database restore.
- **Capacity, overload/headroom, sustained soak, and production operations:** not established by the three short process trials or the 512-fill deterministic owner test. Broader release gates remain in the plan.

The implementation map and scoped passing evidence close Phase 5's local paper requirements. The separate gates above, Phases 7–9 and the rest of the implementation plan remain incomplete. This sign-off does not authorize live execution.
