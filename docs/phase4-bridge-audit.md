This audit maps Phase 4 in [the Go runtime plan, §12](go-runtime-plan.md#12-migration-phases-and-gates) to the committed RPC, Python adapter, training, and benchmark evidence. It records implementation and verification evidence, not phase completion or a decision to switch the training default.

## Measurement and default decision

The retained [`benchmarks/results/optimized-host.json`](../benchmarks/results/optimized-host.json), described in [`benchmarks/README.md`](../benchmarks/README.md), compares a scalar Python reference with Go process-plus-gRPC batches of 1, 8, and 32 environments over two short passes. Terminal outcomes matched exactly. Go measured about 4.4–5.0k, 16.4–16.8k, and 23.0–23.2k transitions/second for the three batch sizes; Python measured about 37.4–45.8k on the corresponding workloads. The measured bridge is slower in this synthetic workload.

This supplies a batched end-to-end comparison, but includes client, serialization, local transport, server dispatch, and replay core together. It does not isolate transport overhead or establish complete PPO training overhead. The §12 instruction is to measure before defaulting; it does not make a positive benchmark result a Phase 4 implementation exit criterion. Keep Python as the default training backend. The separate §16 default-switch criteria include exact economics, feature tolerance, invalid-trajectory handling, policy reevaluation, and section 13 throughput/overhead gates; this audit neither asserts nor closes them.

## Remaining evidence

- The fresh combined run of 216 Python tests remains pending. Existing records show earlier scoped integration evidence, including the Go PPO smoke artifact; they do not substitute for that fresh run.
- The available throughput comparison demonstrates a slower bridge and does not isolate transport or complete training overhead. More representative workload/profile evidence is needed before a Go-default decision, as already described by §16; this is not an invented Phase 4 pass/fail threshold.
- The PPO smoke run establishes API interoperability only. It does not evaluate learning convergence, policy quality, holdout performance, or eligibility for execution.

No other Phase 4-specific missing implementation requirement was identified in the inspected code/tests. The remaining items above are fresh verification, measurement scope, or separate default/policy-quality decisions rather than missing adapter features.
