# Phase 6 Python inference service audit

This draft maps the literal Phase 6 requirements in [the Go runtime plan, §12](go-runtime-plan.md#12-migration-phases-and-gates) to the Python worker, Go inference client, account actor, and retained integration evidence. Phase 6's local implementation checkpoint is recorded in the plan; this audit does not mark the phase complete. The worker and policy bundle remain unvalidated and ineligible for live use. Policy quality, immutable evaluation/promotion, and operational capacity are separate gates.

## Proposal authority and fast market updates

The actor persists a pending request with its parent revision, financial/control `authority_revision`, owner generation, bundle, market snapshot, observation, and expiry before starting the Python RPC. Source-only receipt commits and automatic HOLD bookkeeping can advance the journal without changing financial/control authority. A newer valid market snapshot alone does not invalidate the proposal: the original snapshot remains in the audit binding, while action compilation uses the latest valid book. Fills, reservations, controls, readiness changes, unresolved facts, and ownership recovery do invalidate authority or eligibility. If accepted facts are still behind the processed cursor when a result arrives, the actor does not drain the backlog inline and then apply that proposal: it resolves the pending decision without applying the worker action, and the caught-up readiness requirement prevents a baseline action while debt remains. The authority revision is not a substitute for the journal revision; it separates source/cadence progress from changes that can affect action authorization.

## Validation and remaining gaps

The retained 28 October verification record reports a full Go race run with the real Python worker boundary, 87 Python checks without skips, focused PostgreSQL policy-recovery race repetitions, and an actual worker-backed paper session. Root reports a fresh Go daemon race pass for the current work; full product validation after the archive is still pending. Do not infer a fresh Python worker/full-product pass from the Go daemon result.

- **Duplicate response scope:** `TestPolicyRepeatedAcceptedProposalCannotEnqueueTwice` closes the actor-level duplicate-result regression: the same accepted result is delivered three times after its slot resolves, while one intent/reservation, finances, and authority remain unchanged. This is handler-level result replay only; it does not exercise duplicate network delivery, concurrent RPC responses, or service load.
- **Fast-update cadence:** one source-only trade/new-book case demonstrates that an otherwise valid pending proposal can apply against the latest book. It does not establish behavior under a sustained burst of fast market updates or measure response age/decision latency.
- **Policy evaluation and promotion:** bundles are explicitly `unvalidated` and `live_eligible=false`. No immutable holdout evaluation or promotion authority is evidenced here. The Python model and paper/shadow integration do not establish improved execution economics or eligibility for live use.
- **Operational capacity:** single-flight and bounded deadlines are tested as contracts; the configured account/worker service objectives, multi-account scaling, overload headroom, and sustained soak remain outside the evidence in this audit.

These gaps keep the plan's scope intact. This is an evidence map, not a Phase 6 sign-off or a live-policy authorization.
