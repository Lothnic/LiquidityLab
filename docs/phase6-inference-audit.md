## Proposal authority and fast market updates

The actor persists a pending request with its parent revision, financial/control `authority_revision`, owner generation, bundle, market snapshot, observation, and expiry before starting the Python RPC. Source-only receipt commits and automatic HOLD bookkeeping can advance the journal without changing financial/control authority. A newer valid market snapshot alone does not invalidate the proposal: the original snapshot remains in the audit binding, while action compilation uses the latest valid book. Fills, reservations, controls, readiness changes, unresolved facts, and ownership recovery do invalidate authority or eligibility. If the processed cursor is still behind accepted source facts when a result arrives, the actor does not drain the backlog inline and then apply that proposal: it resolves the pending decision without applying the worker action, and the caught-up readiness requirement prevents a baseline action while debt remains. The authority revision is not a substitute for the journal revision; it separates source/cadence progress from changes that can affect action authorization.

## Validation and separate gates

The [clean combined conformance run](../conformance/results/20261029-contracts-883704c.json) passes all five steps and 216 Python checks with zero skips, failures or errors; all four fixture hashes are unchanged. The [separate full product Go race evidence](../benchmarks/results/paper-accepted-backlog-20261029/README.md#independent-inspection-and-configured-suite) passes with development PostgreSQL and actual Python/replay paths: 1,078 test/subtest pass events, zero skipped test cases, including every named Go regression in this audit and the real tiny-PPO Python worker boundary. Earlier worker-backed paper/worker-loss browser evidence remains recorded in the 28 October verification history. None of these checks is policy-quality evaluation.

- **Duplicate response scope:** `TestPolicyRepeatedAcceptedProposalCannotEnqueueTwice` closes the actor-level duplicate-result regression: the same accepted result is delivered three times after its slot resolves, while one intent/reservation, finances, and authority remain unchanged. This is handler-level result replay only; it does not exercise duplicate network delivery, concurrent RPC responses, or service load.
- **Fast-update scope:** the source-only trade/new-book regression and 100 newer logical book updates in the accepted-proposal regression demonstrate acceptance against the latest valid book while financial/control authority remains unchanged. This closes the perpetual source-revision rejection contract. It does not measure sustained real-time update capacity or response-age/decision latency.
- **Policy evaluation and promotion:** bundles are explicitly `unvalidated` and `live_eligible=false`. No immutable holdout evaluation or promotion authority is evidenced here. The Python model and paper/shadow integration do not establish improved execution economics or eligibility for live use.
- **Operational capacity:** single-flight and bounded deadlines are tested as contracts; the configured account/worker service objectives, multi-account scaling, overload headroom, and sustained soak remain outside the evidence in this audit.

The requirement map and scoped passing evidence close Phase 6's local inference contracts. Operational capacity, policy evaluation/promotion and the remaining product/live gates stay incomplete. This sign-off does not authorize live policies.
